# 第六轮：JNI 字符串解码、ADB 双向桥与 Fastboot 初始化还原

> 分析输入：第五轮完整工程 ZIP。分析对象包括 ARM64 `libadbhelper.so`、JADX Java 源码、assets 以及 ELF 重定位表。  
> 说明：本报告区分“指令/源码直接证实”与“结合调用上下文推断”。未执行 Android 真机或 APK 运行验证。

## 1. 本轮成果概览

1. 修正 `.init_array` 构造函数索引后，按 ELF 重定位顺序识别并模拟了全部 **110 个 `.datadiv_decode...` 字符串解码初始化函数**，共执行约 **244,182 条 AArch64 指令**。解码后的 `.data` 已能读出 JNI 类名、方法名、字段名、签名及部分界面提示文本。
2. 还原 `C0979t3` 的 ADB USB 双向数据桥：本地 TCP 5008 到 USB OUT，以及 USB IN 到本地 TCP，分别对应 `m2631a()` 与 `m2635e()`。
3. 确认 ADB 24 字节消息头为 Little Endian；Native 代码识别 `CNXN` 命令，并在特定 USB 设备标志启用时，将消息头偏移 8 的整数改写为 `0x4000`。
4. 还原 Native 资源释放的关键行为：释放 USB Interface、关闭 USB Connection 和 ServerSocket；另一路清理 ConnectActivity 关联的广播接收器。
5. 从 `FastbootActivity.onCreate()` 的 JNI 元数据与解码字符串中还原 USB attach/detach/permission 广播注册、设备枚举、权限申请、启动 5007 桥接线程，以及未解锁高级功能时的 root 提示对话框。
6. 确认 Fastboot USB 回复回传本地客户端时，Native 方法会以 **8 字节 Big Endian 长度 + payload** 写入 Socket OutputStream。

## 2. 字符串解码初始化

### 2.1 解码执行

- ARM64 `.init_array` 大小 `0x380`，共 112 个指针槽。
- 其中发现 110 个 `.datadiv_decode...` 构造函数重定位项，另有初始化/终结入口。
- 按 `.rela.dyn` 中 `.init_array` 目标地址顺序执行，成功模拟 110 个解码函数。
- 模拟累计约 244,182 条指令，主要指令包括 `adrp/add/ldr/str/ldrb/strb/and/orr/eor/bic/mvn/movi/bsl/bfxil/stp/ldp/ret`。
- 一个可直接核验的解码结果位于数据虚拟地址 `0x1b5788`：`c/c/a/t3`；相邻条目含 `h`、`([B)V`、`java/nio/ByteBuffer`、`allocate` 等 JNI 元数据。

这是对 Native 库加载时字符串初始化过程的静态模拟，不等于在 Android 运行时加载 SO。

## 3. ADB USB 双向桥

### 3.1 Socket → USB OUT：`m2631a(C0979t3)`

**可直接从 AArch64 指令和 JNI 解析表确认：**

- Native 期望类名为 `c/c/a/t3`，入口 JNI 导出符号为 `Java_c_c_a_t3_a__Lc_c_a_t3_2`。
- 首先分配 24 字节数组，并通过 `C0979t3.h(byte[])` 从对象的 `InputStream` 读取。
- 创建 `ByteBuffer`，设置 `ByteOrder.LITTLE_ENDIAN`，再将 24 字节消息头放入缓冲区。
- 读取 `ByteBuffer.getInt(0)` 作为命令字段；指令中的常量 `0x4e584e43` 按小端字节序对应 ASCII `CNXN`。
- 读取对象字段 `m`（JADX 对应 `f4917m`）。源码 `RunnableC0889b3` 仅在 `vendorId == 8921 && productId == 10089` 时将该标志设为 true。
- 当该特殊设备标志为 true 且命令是 `CNXN` 时，指令调用 `ByteBuffer.putInt(8, 0x4000)`，改写消息头偏移 8 的整数。
- 经 `C0979t3.i(byte[])` 将消息头交给 USB OUT 发送路径。
- 从消息头偏移 12 读取 payload length；非零时分配对应长度数组，并通过 `C0979t3.h(byte[])` 从 Socket InputStream 读取 payload；数据再通过 `C0979t3.b(UsbEndpoint, byte[], int)` 进入 USB Bulk Transfer 路径。
- 还会调用 `C0979t3.g(String, ByteBuffer)`、`C0979t3.f(String)` 生成日志，并使用 Handler / Message 传递状态值。

**协议解释：** 24 字节、Little Endian、`CNXN`、偏移 12 的数据长度，与 ADB 消息头结构相符。此处是根据 Native 指令直接使用的常量和偏移作解释；没有在真机抓包验证。

### 3.2 USB IN → Socket：`m2635e()`

JNI 入口 `Java_c_c_a_t3_e__` 的解析表显示：

- 读取对象字段 `c`，其 Java 字段类型为 `UsbEndpoint`；对应 JADX 的 `f4907c`，构造函数按 Endpoint direction 非 0 选择它作为 IN 端点。
- 通过 `C0979t3.b(UsbEndpoint, byte[], int)` 调用统一 USB Bulk Transfer Native 入口读取 USB 数据。
- 使用 `ByteBuffer.LITTLE_ENDIAN` 解析收到的 ADB 消息头，并调用 `g(String, ByteBuffer)` 和 `f(String)` 记录消息。
- 读取消息长度字段，并将头部及数据通过对象字段 `g`（`OutputStream`）调用 `write(byte[])`、`flush()` 回传本地 Socket 客户端。

`RunnableC0974s3.run()` 在建立 5008 Socket 后启动匿名 `r2.run()` Native 线程；`r2.run()` 的 JNI 元数据调用 `t3.e()`，随后异常/退出时调用 `t3.d()`。结合这条线程结构，`m2635e()` 是 USB IN 到 Socket 的接收方向。

### 3.3 配套传输与清理方法

| JADX 方法 | 原始 JNI 名 | 确认行为 | 证据要点 |
|---|---|---|---|
| `m2632b(UsbEndpoint, byte[], int)` | `b` | `UsbDeviceConnection.bulkTransfer()` USB 端点收发入口 | 解析到 `UsbDeviceConnection.bulkTransfer`、`getMaxPacketSize`，并检查 `m/n` 标志 |
| `m2633c()` | `c` | `releaseInterface()`、`UsbDeviceConnection.close()`、`ServerSocket.close()` | JNI 字段/方法解析表直接包含这三项 |
| `m2634d()` | `d` | 先调用 `c()`，再处理 ConnectActivity 关联的广播接收器/清理路径 | 解码到 `c/c/a/t3.c()V` 及 `b/q/a/a` 广播管理对象方法 |
| `m2635e()` | `e` | USB IN 数据读取并转发给 Socket OutputStream | endpoint `c`、`bulkTransfer`、`OutputStream.write/flush` |
| `m2636f(String)` | `f` | 使用 ConnectActivity/MyApplication 上下文的日志输出入口 | JNI 解析到 `getApplicationContext()`、`MyApplication` |
| `m2637g(String, ByteBuffer)` | `g` | 包装 `C0978t2(ByteBuffer)` 并生成消息头日志 | JNI 解析到 `c/c/a/t2` 构造器及 `toString()` |

| `m2639i(byte[])` | `i` | 获取字段 `b` 的 USB OUT Endpoint 并调用 `b(...)` | JNI 解析到 `UsbEndpoint` 字段 `b` 与方法 `b(UsbEndpoint,[B,I)` |

## 4. Fastboot 初始化与数据回传

### 4.1 `FastbootActivity.onCreate()`

从 Native 方法解析表及解码字符串可确认：

- 初始化布局、Toolbar、TextView、ImageView、Button、Spinner、EditText，并绑定多个 Listener。
- 注册 `android.hardware.usb.action.USB_DEVICE_ATTACHED`、`android.hardware.usb.action.USB_DEVICE_DETACHED` 以及 `com.didjdk.adbconnect.usb.permission` 广播。
- 获取 `UsbManager`，读取 Intent 中的 `device` extra，并枚举 `UsbManager.getDeviceList()`。
- 对设备调用 `hasPermission()`；无权限时创建 PendingIntent 并调用 `requestPermission()`。
- 启动 `Thread(new c/c/a/g0(...))`，对应 Java 中的 `RunnableC0911g0`，它创建 TCP `ServerSocket(5007)`。
- 读取 `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` 权限状态并触发权限请求路径。
- 读取 SharedPreferences 键 `show_fastboot_dialog`。Native 字符串中出现提示：“您还没有解锁高级功能，只能以root权限运行fastboot命令。”并包含“不再提示”“取消”“解锁”“使用root运行”等对话框文案。
- 存在 `b/s/m.L(Context)` 返回字符串后与 `yi4on8` 比较的分支。当前只能确认该比较存在，不能仅凭常量认定它对应哪种授权语义。

### 4.2 USB 广播 `C1321d.onReceive()`

- 分支识别 USB_DEVICE_DETACHED 与 USB_DEVICE_ATTACHED。
- 断开时可显示“设备已断开”，并通过 Handler 发消息。
- 插入时记录 `ATTACHED-device`、`PERMISSION-device` 等日志。
- 检查设备是否为 Fastboot 目标；失败分支提示“插入的设备不是fastboot设备”。
- Native 代码通过 `m3016x(FastbootActivity, UsbDevice, UsbInterface)` / `m3022y(UsbDevice)` 等入口处理 USB 设备。
- 对未授权设备通过 PendingIntent 与 `UsbManager.requestPermission()` 申请权限。

### 4.3 USB 接口检查线程

`FastbootActivity$C1319b.run()` 的 JNI 元数据显示它遍历 `UsbDevice.getInterfaceCount()` / `getInterface(i)`，读取 `getInterfaceClass()`、`getInterfaceSubclass()`、`getInterfaceProtocol()` 并记录组合值，随后通过 `runOnUiThread()` 更新 UI，并调用 FastbootActivity 的 USB 接口处理入口。

### 4.4 Fastboot 回传 framing

Native 入口 `FastbootActivity.m3021E(byte[], int)`（原始方法名 `E`）解析到：

- `ByteBuffer.allocate()`；
- `ByteOrder.BIG_ENDIAN`；
- `putLong(length)`；
- `put(payload, offset, length)`；
- 字段 `a0`（JADX 对应 `f6407a0`，OutputStream）；
- `OutputStream.write(byte[])` 与 `flush()`。

因此 Native 将 USB 返回数据包装为 `8 字节 Big Endian 长度字段 + payload`，写入 Fastboot 本地 Socket。该格式与 Java `RunnableC0911g0.run()` 从 5007 Socket 读取 8 字节长度字段的行为相符。

## 5. 极重要：JADX 重命名与 JNI 绑定冲突

反编译工程中存在大量 `JADX INFO: renamed from ...` 标记。以本轮核心类为例：

- `p080c.p113c.p114a.C0979t3` 原始类名为 `c.c.a.t3`；
- `p080c.p113c.p114a.C0978t2` 原始类名为 `c.c.a.t2`；
- `C0979t3.m2631a` 原始方法名为 `a`，其余 Native 方法依次为 `b` 至 `i`；
- `FastbootActivity.m3016x`、`m3017A`、`m3018B`、`m3019C`、`m3020D`、`m3021E`、`m3022y`、`m3023z` 对应原始方法名 `x/A/B/C/D/E/y/z`。

Native resolver 字符串明确解析 `c/c/a/t3` 的类名、字段 `b/m/l/k` 和方法 `h/g/f/i/b`；导出符号也使用 `Java_c_c_a_t3_a...`。因此，仅将 JADX 当前显示的安全化类名和方法名原样编译，不能满足 Native 代码期望的二进制类名、字段名、方法名。字段名同样需要恢复（例如原始字段 `b` 对应 JADX 字段 `f4906b`）。

**工程恢复建议：** 应先以 JADX 注释生成全工程原始类/字段/方法映射表，再整体恢复 JNI 所依赖的原始二进制名称；不能只给 `C0979t3` 加一个简单 wrapper，因为 Native 还按原名访问多个字段和方法。另一条路线是重写 JNI 注册映射/修改 Native resolver，但工作量和风险更高。

## 6. 可读伪代码（按已证实行为整理，不是原始 C++）

```java
// 示意：还原 ADB socket -> USB OUT 主路径。
// 具体异常、短读重试、进度消息和所有分支仍需逐块补齐。
void relayAdbSocketToUsb(C0979t3 t) {
    byte[] header = new byte[24];
    t.m2638h(header); // Native: 从 TCP InputStream 读入

    ByteBuffer frame = ByteBuffer.allocate(24)
            .order(ByteOrder.LITTLE_ENDIAN)
            .put(header);

    int command = frame.getInt(0);
    if (t.f4917m && command == 0x4e584e43) { // 'CNXN' (LE)
        frame.putInt(8, 0x4000);
        header = frame.array();
    }
    t.m2639i(header); // Native: 发往 USB OUT

    int payloadLength = frame.getInt(12);
    if (payloadLength > 0) {
        byte[] payload = new byte[payloadLength];
        t.m2638h(payload); // Native: 从 TCP InputStream 读 payload
        // Native 实现按内部分支处理 Bulk OUT 传输和进度更新。
        t.m2632b(t.f4906b, payload, payloadLength);
    }
}
```

上面的 Java 是语义草图，不应直接替换原生实现；真实 Native 函数还包含消息日志、Handler 通知、异常分支、局部引用释放及大包处理分支。
