## 3. 发现的两个确定性构建结构问题

### A. Native 库目录不是 AGP 默认目录

当前 `.so` 位于：

- `app/src/main/lib/arm64-v8a/libadbhelper.so`
- `app/src/main/lib/armeabi-v7a/libadbhelper.so`

Android Gradle Plugin 默认 JNI 库目录为 `src/main/jniLibs`。若保留原目录，需要在 `sourceSets` 显式将 `src/main/lib` 配为 `jniLibs.srcDirs`；候选配置已写入 `app_build.gradle_候选修复`。

### B. `R.java` 是 JADX 生成文件

当前源码有 `app/src/main/java/com/didjdk/adbhelper/R.java`，文件头标注 `This class is generated by JADX`。Android Gradle Plugin 会根据 `src/main/res` 自动生成 R 类；构建时应排除此手工生成文件，以免与 AGP 生成类重复。候选配置已加入 Java source exclude。

APK 解出的 Manifest 自身带有 `android:compileSdkVersion=23` 和 `platformBuildVersionCode=30` 元数据，与 module Gradle 文件的 compileSdk 28 不一致。Gradle 构建以 module 配置为准；该差异需在成功构建后再核对，不应据此随意修改 targetSdk。

## 5. 当前依赖策略建议

目前没有足够证据恢复原始 Maven dependency 坐标和准确版本。与此同时，反编译工程已经把大量 AndroidX、Material、Glide / 图片处理相关保留类放入 `src/main/java`，而 import 扫描未发现明显缺失的非平台类型。因此不建议现在随意添加一组版本猜测的 `implementation` 依赖，否则可能出现重复类。

应先应用候选构建结构修复，随后在具备 Android SDK / Gradle 的环境执行编译；以第一批实际缺失类型、资源符号和重复类错误决定是否外部化源码或添加 Maven 依赖。
